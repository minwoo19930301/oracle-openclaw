# 구축·검증 절차

이 문서는 실제 설치 경험에서 재사용할 판단과 검증 순서를 정리한다. 운영 서버 주소나 인증 정보는 포함하지 않는다. 아래 SSH 명령의 `OCI_HOST`는 사용자가 제공한 SSH 별칭이다.

## 1. 기존 환경 조사

```bash
ssh OCI_HOST 'uname -m; cat /etc/os-release; free -m; df -h'
ssh OCI_HOST 'systemctl list-units --type=service --all | grep -i openclaw'
ssh OCI_HOST 'systemctl --user list-units --type=service --all | grep -i openclaw'
ssh OCI_HOST 'ss -lnt'
ssh OCI_HOST 'docker ps --format "{{.Names}}\t{{.Image}}\t{{.Ports}}"'
```

없는 도구의 오류는 미설치로 구분한다. 읽기 실패를 이유로 전체 설정·환경변수를 덤프하지 않는다. 서비스 파일과 Docker 설정은 비밀이 포함될 수 있으므로 필요한 필드만 추출한다.

- 사용자 systemd와 시스템 systemd, Docker를 구분한다. 기존 서비스와 같은 이름의 두 번째 Gateway를 만들지 않는다.
- ARM64 VM에는 `linux/arm64` 이미지와 바이너리를 선택한다. 메모리는 실제 여유량과 브라우저/모델 사용량에 맞춰 배분한다.
- OCI 보안 규칙과 호스트 방화벽, Docker publish를 각각 확인한다. 기존 SSH 접근을 먼저 끊지 않는다.

## 2. OpenClaw 설치 또는 복구

기존 OpenClaw가 정상 운영 중이고 변경 요청이 없으면 이 절의 설치·복구·모델 재설정은 생략한다.

현재 [공식 설치 경로](https://docs.openclaw.ai/install/oracle)와 OS에 맞는 패키지·Node 요구사항을 확인한다. 버전·상태 디렉터리·실행 사용자·서비스 환경파일 위치를 기록한다.

- 새 설치에서는 전용 실행 사용자와 지속 실행을 구성한다. 기존 환경이면 사용자·상태 경로·메신저 연결을 유지한다.
- 모델 provider, 모델 ID, 인증값을 각각 다룬다. 기존에 특정 공급자가 연결되어 있으면 별도 요청 없이 바꾸지 않는다.
- 실제 인증값은 서버의 제한된 환경파일 또는 지원하는 secret store에 둔다. Git 예시에는 값 없이 변수명만 둔다.
- 호스트에서 직접 실행할 때는 관리 Gateway를 loopback에 두고 SSH 터널 등으로 접근할 수 있다. 컨테이너 내부 loopback은 호스트 loopback과 다르므로 Docker의 내부 bind와 호스트 포트 공개 주소를 별도로 설정한다.
- 메신저는 의도한 사용자·방만 허용한다. 기존 bootstrap의 `allowFrom: ['*']`, TLS 예외, 과도한 도구 권한을 새 환경에 자동 복사하지 않는다.

대상 VM에 접속한 뒤 기존 서비스 실행 사용자로 서비스 방식과 설치 버전을 확인한다. 그 환경에서 지원되는 명령만 사용한다. 예:

```bash
openclaw --version
openclaw gateway status
openclaw health
```

Doctor가 설정·상태를 변경하는 모드인지 도움말로 먼저 확인한다. 업데이트 전 상태 백업을 남기고, 마이그레이션 뒤에는 이전 바이너리만 덮어쓰는 복구를 피한다.

## 3. 선택 사항: 협업 웹앱 구축

[구성 요소 문서](architecture.md)의 웹 계층이 실제 저장소에 존재하는지 확인한다. 없으면 구현 후 로컬에서 검증한다. OpenClaw 하나만 요청된 작업에는 이 계층을 추가하지 않는다.

- Node.js 앱: 계정·방·첨부 권한을 서버에서 검증한다. 비밀번호는 개별 salt로 해시하고, 세션 쿠키·CSRF를 적용한다. 사용자에게 보여줄 과금/호출 제한을 정하고 모든 모델 호출에 적용한다.
- 저장소: SQLite와 업로드 파일을 영속 볼륨에 둔다. DB를 실행 중 복사할 때 SQLite backup API를 쓰거나 앱만 중지해 DB/WAL을 함께 보존한다.
- 모델 어댑터: endpoint·model·secret이 모두 준비됐을 때 봇을 활성화한다. `model.configured` 같은 명시적인 상태를 제공하고, 미연결은 사람 대화와 구분한다.
- 공유 데스크톱: Chromium sandbox를 유지하고 비특권 사용자로 실행한다. unrelated room은 별도 컨테이너를 사용한다. 앱의 방 권한 검사 뒤에만 noVNC/CDP가 접근되게 한다.
- 네트워크: 앱·데스크톱·HTTPS 프록시를 분리하고, VNC/CDP와 Docker socket을 공개하지 않는다. 브라우저 도구가 OCI metadata·다른 사설 자원으로 접근하지 못하도록 애플리케이션 검사와 실제 네트워크 경계를 함께 검증한다.

공유 데스크톱의 브라우저 로그인 상태는 같은 방 멤버에게 보인다. 임시 저장소라면 컨테이너 재생성 시 다운로드·로그인 상태가 사라짐을 명시한다. 첨부 업로드와 모델의 이미지 인식·음성 전사는 별개 기능이다.

## 4. 배포·운영

기존 OpenClaw와 충돌하지 않는 포트·서비스 이름·볼륨을 선택한다. 승인된 대상에만 적용하고 실제 VM 규모·계정 과금 조건을 보존한다. 설치 문서의 무료 사양 예시를 계정의 비용 보장으로 쓰지 않는다.

공유 앱이 Compose로 구현되어 있다면 실제 경로에서 build → 구성 검사 → up 순서로 적용한다. `docker compose config`는 secret을 펼칠 수 있으므로 출력 내용을 로그로 남기지 않고 검증용 quiet 옵션을 사용한다. 볼륨을 지우는 `down -v`는 업데이트 절차에 넣지 않는다.

모델 검증 요청과 실제 메신저 전송은 별도다. 모델 호출만 허가된 경우 메신저에 대신 메시지를 보내지 않는다. 외부 메시지 전송이 명시된 작업이면 지정된 수신자·본문으로 한정해 검증한다.

## 5. 완료 기준

| 확인 | 근거 | 확인되지 않은 것으로 남길 것 |
| --- | --- | --- |
| 프로세스·재시작 | 선택한 서비스의 health, 재시작 뒤 같은 상태 경로 | 장기간 무중단 운영 보장 |
| 모델 | 지정한 모델의 실제 최소 응답 | mock 통과로 실제 모델 연결 추정 |
| 메신저 | 채널 연결 상태, 허가된 경우 실제 왕복 | CLI 답변만으로 메시지 전송 성공 추정 |
| 웹앱 | 로그인·방·첨부의 허용/거부 테스트 | HTTP 200만으로 권한 격리 추정 |
| 데스크톱 | 허가된 방 조작, 무권한 방·로그아웃 접근 거부 | 모든 방에 자동 provision되었다는 주장 |
| 복원 | 백업 존재, 합성 데이터 또는 격리 환경의 복원 확인 | 백업 생성만으로 복원 성공 주장 |

보고에는 구성도, 릴리스/버전, 실제 검증 결과, 모델 연결 상태, 복구 경로만 남긴다. 인증값과 개인 데이터는 포함하지 않는다.
